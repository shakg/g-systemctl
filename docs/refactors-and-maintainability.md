# Refactors and Maintainability Improvements

This document tracks codebase refactors and maintainability improvements for `g-systemctl`.
Use it as a backlog for changes that reduce risk, simplify future work, or make platform
behavior easier to test.

## Prioritization Guide

- **High impact:** Improves correctness, command safety, testability, or platform behavior.
- **Medium impact:** Reduces duplication, clarifies ownership, or makes the UI easier to extend.
- **Low impact:** Improves naming, documentation, formatting consistency, or developer ergonomics.

## High Impact

- [ ] Replace shell-concatenated command strings with structured command execution.
  - Current service operations build commands by concatenating unit names into shell strings.
  - Prefer an executor API that accepts a program plus argument list, escapes arguments centrally,
    and avoids invoking `/bin/sh` where possible.
  - This affects `SystemCommandExecutor`, Linux service commands, macOS service commands, and log commands.

- [ ] Define explicit result/error types for service actions.
  - `ServiceManager` currently returns `std::pair<bool, std::string>`, which makes call sites depend on
    positional meaning.
  - Introduce a small `ServiceActionResult` type with `success`, `message`, and optionally `exit_code`.
  - This will make UI status and error handling easier to read and safer to extend.

- [ ] Split `App` into smaller UI/state units.
  - `App` currently owns data loading, filtering, input handling, auth prompts, log streaming, and rendering.
  - Consider extracting:
    - `ServiceListState` for filtering, selected index, and service list operations.
    - `LogPanelState` for log lines, scroll position, follow-tail behavior, and stream lifecycle.
    - `AuthDialogState` for pending action, password input, and dialog transitions.
  - Keep FTXUI rendering thin and move state transitions into testable classes.

- [ ] Add tests for UI-independent state transitions.
  - After extracting state classes, cover filtering, selection clamping, log scrolling, follow-tail behavior,
    and auth action submission without starting an FTXUI screen.
  - This gives the fastest feedback for regressions in keyboard and mouse behavior.

- [ ] Harden command output parsing.
  - Linux parsing depends on whitespace tokenization of `systemctl` output.
  - Consider using `systemctl show` properties or another stable machine-readable format where available.
  - Keep unit file parsing and live unit parsing separate, with fixtures for common edge cases.

## Medium Impact

- [ ] Centralize platform command construction.
  - Linux command prefixes such as `systemctl` vs `systemctl --user` are repeated.
  - Introduce small helpers for service mode, log mode, and privileged actions to keep behavior consistent.

- [ ] Improve platform interface symmetry.
  - Linux and macOS implementations expose the same service manager interface but have different command semantics.
  - Document which fields in `ServiceUnit` are guaranteed, optional, or platform-specific.
  - Keep UI behavior based on those guarantees instead of platform-specific assumptions.

- [ ] Normalize status and lifecycle concepts.
  - Service status is currently inferred from string fields such as `active`, `sub`, and `is_running()`.
  - Consider adding a normalized enum for display state, while preserving raw platform fields for diagnostics.

- [ ] Make refresh and service actions non-blocking.
  - Service actions and refreshes can block the TUI while commands execute.
  - Consider moving long-running operations to worker tasks and posting results back to the UI event loop.
  - Keep cancellation and duplicate-action behavior explicit.

- [ ] Extract reusable formatting helpers from `src/ui/app.cpp`.
  - Cell rendering, colors, and status formatting are embedded in the main UI implementation.
  - Move stable formatting helpers into dedicated UI modules when they are used by more than one render path.

- [ ] Add integration-style tests with fake command executors.
  - Expand command executor fakes to verify exact commands or argument vectors generated by service managers.
  - Include Linux system mode, Linux user mode, macOS load/unload, restart, and failure cases.

## Low Impact

- [ ] Keep documentation terminology consistent.
  - Use `system services`, `user services`, `logs`, and `service units` consistently across README, help text,
    and in-app labels.

- [ ] Add a short architecture note.
  - Document the current ownership boundaries:
    - `core`: service/logging interfaces and command execution.
    - `platform`: Linux and macOS implementations.
    - `ui`: FTXUI app state, input handling, and rendering.
  - This helps contributors place new code without reading every source file first.

- [ ] Document supported compiler and dependency versions in one place.
  - README lists prerequisites; CMake encodes build requirements.
  - Keep these aligned and consider adding a short dependency update checklist.

- [ ] Consider a formatting/linting command.
  - If the project standardizes on `clang-format` or `clang-tidy`, add Makefile targets and CI checks.
  - Start with formatting only if full linting is too noisy.

## Suggested Order

1. Introduce explicit result types for service actions.
2. Add fake-executor tests around current platform behavior.
3. Refactor command execution toward structured arguments.
4. Extract UI-independent state from `App`.
5. Add state transition tests.
6. Revisit asynchronous refresh and service actions once state ownership is clearer.

## Notes for Contributors

- Keep refactors behavior-preserving unless the pull request explicitly describes a user-visible change.
- Prefer small pull requests that isolate one boundary at a time.
- Add tests before or alongside changes that affect command execution, platform parsing, or UI state transitions.
- Avoid mixing formatting-only changes with logic changes.
